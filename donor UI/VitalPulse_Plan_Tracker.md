## GUARDRAILS (non-negotiable — from AGENT.md & Security Master Plan)

1. **Stack is locked.** Vite + vanilla JS + Tailwind v4 + Firebase SDK + Leaflet + Chart.js. No new libraries without Security Lead sign-off.
2. **Schema freeze is active** (Phase 2.5). No new Firestore collections or fields without Security Lead approval. Auth work introduces a **new, KYC-only** `donors/{uid}` collection (`kycStatus`, `kycDocType`, `kycDocRef`, `kycSubmittedAt`) — approved 2026-08-01 (see Stream A4). It does not replace or migrate anything on `users/{uid}`; existing donor profile data (blood type, points/tier, badges, notification prefs) stays exactly where it is today.
3. **Zero trust on the client.** `kycStatus`, `role`, and `suspended` are never written from the client. Only Cloud Functions write them.
4. **No PHI in logs, URLs, or error messages.** Password is never stored, logged, or passed to any function — Firebase Auth owns it entirely.
5. **Don't touch** `hospital.html`, `admin.html`, or shared auth routing in `main.js` beyond what the EN/FR language toggle needs.
6. **Don't break the existing view-switch engine.** All donor screens live in `donor.html` + `donor-dashboard.js`. New markup slots into the `switchDonorView()` / `.donor-mobile-nav` / `data-action="switch-view"` contract.
7. **One screen per commit.** Small, reviewable commits. Auth/rules changes require two reviewers — Security Lead must be one.
8. **Definition of done:** code written → tested in dev server (desktop + mobile) → existing vitest suite green → tracker row flipped to ✅ in the same commit.

### Decisions locked in 2026-08-01 (before any C-stream code was written)

1. **Sign Up collects BOTH email and phone, both required.** Resolves a real conflict found comparing the mockups: "Sign Up - Account Details" shows no email field, but "Sign In" accepts "Phone or Email" and the Forgot Password flow is Firebase's standard email-link reset (`sendPasswordResetEmail`), which needs a real, deliverable email on every account. Your call, not assumed.
2. **Forgot Password asks the donor which channel to receive the reset link on** (not just email). Implemented consistent with how this app already handles SMS/WhatsApp everywhere else (`notification_log`, `sendSmsNotification`/`sendWhatsAppNotification` in `db.js` — a generated deep-link the donor opens themselves; no real SMS/WhatsApp Business API gateway is integrated anywhere in this project). Email delivery is real (Firebase sends it natively). WhatsApp "delivery" is the same honest pattern as the rest of the app: a Cloud Function generates the real Firebase reset link server-side (`admin.auth().generatePasswordResetLink`), and the client opens a pre-filled `wa.me` link containing it for the donor to send to themselves — not an automated push.
3. **Sign Up gets a new, mandatory Blood Group field** (dropdown: A+/A-/B+/B-/O+/O-/AB+/AB-, matching the existing `bloodType` enum used everywhere else in the app) **plus an explicit "I don't know my blood type" option.** Not in the mockup — added at your direction. ### New Cloud Function needed for C1 (Sign In), found while implementing, not in the original B-stream list

`resolveSignInIdentifier` (callable, unauthenticated by necessity — same class as `checkPasswordBreach`, called before any session exists): `signInWithEmailAndPassword` requires a real email, but the Sign In mockup accepts a phone number too, and an unauthenticated client cannot query `users` directly (`firestore.rules`: `allow get, list: if hasRole()` — deny by default, no anonymous-lookup exception). This function resolves a phone number to its account's email server-side via the Admin SDK (bypasses rules by design), or passes an email straight through unchanged. Returns `{ email: string|null }` either way — never a distinct "phone not found" vs "wrong password" signal, so it can't become a account-enumeration oracle and stays consistent with C1.2's "always show one generic error" requirement.

## STREAM D — PENDING & VERIFIED DASHBOARD STATES
*Work in `donor.html` + `donor-dashboard.js`. Depends on Stream B being live.*

### Decisions/simplifications made while building, 2026-08-01

1. **"Persistent" banner lives at the top of the dashboard view, not injected into every donor sub-view's markup.** A truly global banner would mean touching the shared shell every view renders inside, which none of the individual views currently own — riskier and more invasive than this feature calls for. Donors reliably see it every time they land on Home (their default landing view), which is where D2/D5/D7 belong anyway. Flagged as a scope simplification of "persistent," not a silent gap.
2. **"Blur + lock icon overlay" implemented as a `backdrop-blur` overlay layered on top of each locked element, not literal `filter:blur()` on the element itself.** `filter:blur()` on an interactive `<button>` blurs its whole subtree, including a lock badge you'd want to render *sharp* on top of it — fighting that with z-index/filter tricks is fragile. A sibling/child overlay with `backdrop-filter: blur()` blurs what's *behind* it while staying crisp itself, which is the actual visual effect "blurred card with a lock icon on it" was going for, and reuses the exact `hidden`/`flex` toggle convention already used elsewhere in this file (e.g. the KYC doc-type check badges).
3. **Grandfathered accounts (no `donors/{uid}` doc — everyone who signed up before this feature existed) are always treated as verified, never locked.** Same rule `firestore.rules`' `isKycEligible()` already uses server-side; the client mirrors it so pre-existing users don't suddenly find scheduling/accepting locked with no way to become "verified" (they were never assigned a `kycStatus` at all).
4. **Real security boundary stays server-side, as with every other client-side gate in this app.** These locks are UX — they stop a genuine donor from being confused by a button that would just fail server-side. `window.donorAcceptRequest` gets its own independent `warnIfKycPending()` check (not just a disabled button) as defense-in-depth, but the actual enforcement is, and must remain, whatever the accept/schedule Cloud Functions check server-side.

## STREAM I — KYC UPLOAD HARDENING + MAP/COPY FIXES, 2026-08-03

Security Lead's report from testing the live KYC upload flow: a stray SHA-256 claim on the National ID field, National ID only ever asked for one side of the card, a "skip verification" affordance still existed even though verification is mandatory, `submitKYC` threw `internal` in the browser console, and the donor dashboard's Cameroon map didn't visually match `001_Donor Portal - Home Dashboard (Elevated).png`.

1. **Removed the "🔒 Protected with SHA-256 hashing. Raw ID is never stored." line** under the National ID field (`donor.html`) — it was a UI claim with nothing enforcing it in view; the National ID is in fact SHA-256 hashed before being written (`hashNationalId()` in `donor-dashboard.js`'s KYC submit handler), but that claim belongs in documentation/audit evidence, not as an unverifiable badge next to a plaintext input.
2. **National ID now requires both a front and back image; every other doc type is unchanged (still one page).** Schema-enforced, not just a UI nicety: `submitKycSchema` (`functions/src/schemas.ts`) gained optional `fileBackBase64`/`fileNameBack`/`mimeTypeBack`, required together via `superRefine` specifically when `docType === 'national_id'`. `submitKycHandler` uploads both faces to `kyc/{uid}/national_id_*.jpg` / `kyc/{uid}/national_id_back_*.jpg` and stores the second path as a new `kycDocBackRef` field on `donors/{uid}` (schema-freeze exception, same precedent as `livenessSelfieRef` in Stream G — flagged here, not silently added). Client UI (`donor.html`/`donor-dashboard.js`) shows a second upload zone only when National ID is selected, and the Submit button now requires both files. Admin review queue (`main.js`) gained a "Back" document button alongside "Front"/"Selfie", shown only for `national_id` rows.
3. **Removed the "I'll complete this later" skip links on both the document-upload step and the liveness step.** Verification is mandatory — these were the only literal skip affordances in the KYC flow (the rest of the app already treats an incomplete account as locked via Stream D's `isDonorKycSkipped()`/`applyKycLocksToDOM()`, which is unchanged and still the real enforcement boundary; this just removes the UI invitation to walk away mid-flow).
4. **Root-caused the `submitKYC failed: FirebaseError: internal` error.** `functions/src/firebaseAdmin.ts` called `initializeApp()` with no explicit `storageBucket`; this project's default bucket uses the newer `<project-id>.firebasestorage.app` naming (confirmed against `vitalpulse_app/.env`'s `VITE_FIREBASE_STORAGE_BUCKET`), and Cloud Functions v2's ambient `FIREBASE_CONFIG` auto-detection is known to still resolve the legacy `.appspot.com` name for projects on this newer scheme — pointing `getStorage().bucket()` (used by every KYC upload) at a bucket that doesn't exist, thrown as an uncaught exception the `onCall` wrapper converts to a generic `internal` error. Fixed by passing `storageBucket` explicitly at `initializeApp()`. **This fix requires a Cloud Functions redeploy to take effect — not yet deployed.** I do not have deploy credentials for this Firebase project from this environment (confirmed via `firebase projects:list`, which does not list `vitalpulse-fa458`); the Security Lead needs to run `firebase deploy --only functions` (or equivalent CI) after reviewing this change. The browser console's other errors (`QUIC_PROTOCOL_ERROR`, `ERR_CONNECTION_RESET` on `firestore.googleapis.com`) are local network/QUIC issues, unrelated to this bug and outside what a code change can fix — worth ruling out separately (try disabling QUIC in `chrome://flags`, or testing on a different network) if Firestore reads/writes are also unreliable after this deploy.
5. **Cameroon map visual pass (`renderNearbyMap`/`renderCentersMap`, `donor-dashboard.js`).** The mockup shows a clean, illustrated, label-free Cameroon map; Stream E had deliberately replaced an earlier schematic placeholder with a real Leaflet/OpenStreetMap map so markers reflect real donor/hospital/request coordinates instead of a static decoration — that tradeoff stands (a real map is more useful and this project's standing rule is not to fake data), but its styling didn't match. Switched the CARTO tile layer from `light_all` to `light_nolabels` (removes street/place-name clutter), added a real Cameroon bounding box (`maxBounds`, `minZoom: 6`) so the map stays framed on the country instead of drifting into the ocean or neighboring countries, and added small DOUALA/YAOUNDÉ/BUEA text labels via Leaflet `DivIcon` at their real coordinates (reusing the existing `CITY_COORDINATES`, the same three cities already in the UI's city-filter chips) to replace the labels the tile switch removed. No fabricated geography — no hand-drawn country outline was added, since this codebase has no verified GeoJSON boundary for one and guessing one would violate the project's data-integrity principle; this is real markers on a real, cleaner-styled map, not a redraw of Cameroon's borders.
